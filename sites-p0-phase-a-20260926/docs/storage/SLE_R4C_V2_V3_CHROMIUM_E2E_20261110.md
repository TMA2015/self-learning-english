# SLE Issue #103 — R4c cross-format V2→V3 browser recovery acceptance

**Status:** research QA only, Draft; no release, no migration  
**Date:** 2026-11-10  
**Authority:** Current SLE-MASTER-001 on `main`. This file is evidence, not an additional active standard.

## Why this test is necessary

Draft #108 proves original-format V2→V3 transformation with public curriculum and 73 synthetic attempts in Node. Draft #109 independently proves normalized V3 export/restore with real Chromium IndexedDB using a generated synthetic source. Neither individually demonstrates an end-to-end restore **starting with an original-format V2 backup** inside a real browser.

R4c exercises that missing boundary. The initial research branch was stacked on Draft #111, but the scope has been reconciled to the current `main` base: this PR now copies **only five isolated R1–R4 recovery-support modules**, two new browser-test files, the existing QA-list registration, and the bounded FFmpeg mirror fallback. It does **not** include the unmerged R5 AcademicService or progress changes. These copied research modules are still **not wired to the production runtime** and cannot authorize merging or migration.

## Exact scope

- Uses *committed public* curriculum sources `1.18.0`, `1.18.1`, `1.20.0`; derives deterministic source checksums. No real user file is accessed.
- Constructs an authentic **V2 file-format** checksum from 3 cumulative public versions and exactly **73 synthetic attempts**: 52 marked scored, 21 started. It includes invented Writing state/reviews and course-selection state; this is **not a real V2 export from an iPad**.
- Verifies original V2 archive with the existing production-format parser; converts via the unmerged read-only V2→V3 adapter; verifies resulting V3 checksum and original values byte-for-byte.
- Uses real throwaway localhost Chromium profile and IndexedDB, initially empty. Proves invalid original V2 checksum is rejected; occupied-profile restore preview is rejected without overwriting the synthetic sentinel.
- Performs confirmed restore only into empty **disposable** profile. Checks the exact serialized attempts, Writing/review and course-state entries; requires the old cumulative package key is not recreated.
- Reads original historic Vocabulary, Reading and Writing lesson/rubric content from IndexedDB aliases; distinguishes original changed lessons from the latest revision; re-exports a verified complete V3.
- Fully closes/reopens a separate Chromium process and checks that 123 active public lessons, historical aliases, serialized attempts and verified V3 export remain available. The driver requests normal browser shutdown through Chrome DevTools Protocol `Browser.close` and verifies process exit before relaunch, rather than sending SIGTERM on successful test phases. This distinguishes an ordinary restart from a hard process kill, **not** power-loss/crash resilience. A failed restart comparison reports only synthetic lengths, hashes and storage key names. Earlier headless Chromium QA using SIGTERM observed empty localStorage after restart while IndexedDB survived; this finding is not resolved until the normal-shutdown run passes.

The test is registered as one additional test under the existing `qa:core`/`qa:full`. It does not create workflows, alter web app runtime, change current LIVE curriculum, enable background migration, or touch Firebase.

## R4d extension — interrupted cross-store restore on real disposable Chromium

The existing R4c harness now performs a second, isolated three-process scenario on a separate ephemeral browser profile:

1. A deterministic, checksum-correct V2 **test fixture** is converted to V3 and verified. A scoped test adapter delegates to real Chromium `localStorage` but raises a **synthetic `QuotaExceededError` once** at the course-selection key, **after** the 73-attempt key was written.
2. The interrupted V3 adapter must roll back the newly written attempt key without overwriting any learner record, preserve the V3 `recovery-pending-v3` marker, and preserve the atomic original revision and alias content in **real IndexedDB**. The partially restored profile must reject V3 exports and an independently valid but different V3 file.
3. Chromium is shut down **normally** using `Browser.close`; a new process must find the same pending marker and original IDB sources. Re-selecting only the identical verified V3 file completes the restore. The test then checks 73 original synthetic attempt strings, Writing/reviews, course selection and historic Writing source/rubric; a complete V3 re-export must succeed.
4. A third independent Chromium process verifies that the completed learner and IDB sources persist, with **no remaining interrupted marker**.

**Strict boundary:** The interruption is **fault-injected into a localStorage adapter**, *not* a genuine native Safari/Chromium quota exhaustion, a process crash, or a power-loss test. Real browser IndexedDB transactions, browser restarts, localStorage persistence and actual recovery code are exercised, but cross-browser Safari acceptance remains open. A failed test must remain blocking; no QA gate or backup validation may be loosened to obtain PASS.

## R4e extension — **actual native Chromium localStorage quota**

This further extends the same disposable browser harness with a **third, separate ephemeral Chromium profile**; R4c and R4d retain their existing QA assertions. A scratch key outside the English learner namespace is populated by binary-searching native `Storage.setItem` capacity. The test **must observe a real `QuotaExceededError` thrown by Chromium** with the original browser storage implementation, not a fault-injecting wrapper. If the runner has no observable native quota boundary inside the test range, this test **FAILS** rather than falsely reporting PASS.

With roughly 4,096 code units of headroom, the R4e test performs the verified V2→V3 empty-profile Restore using the actual `localStorage` and real IndexedDB. It requires a native quota exception during the 73-attempt payload write; it then proves that there are no half-written learner entries, the correct V3 interrupted marker persists, normalized history remains available in real IndexedDB, and incomplete backup export is blocked.

After a graceful `Browser.close` and fresh Chrome process, the test verifies that the interrupted state persisted. It removes **only its own scratch padding key**, does not touch owner-scoped learner data, and resumes **the same checksum-verified V3**. It then checks 73 byte-identical synthetic attempts, Writing/reviews, course state, original historical Writing rubric, cleared marker, and complete V3 export. One more independent Chrome restart confirms persistence.

**Meaning and limits:** This is a **native Chromium localStorage quota** test, not actual Safari quota, not actual IndexedDB write-quota exhaustion, not an iPad test, and not an abrupt crash/power-loss test. The first failure is a native browser quota error, while the extra padding and learner records are test-owned and disposable. Real family Recovery and real learner data remain untouched.

## R4f extension — real IndexedDB blocked versionchange / fail-closed

A **fourth, completely disposable Chromium profile** tests native IndexedDB schema-version contention, separate from R4c–R4e:

1. Build checksum-verified V2 from three *public* curriculum sources with **73 fake attempts**; convert to V3 and restore to empty localStorage plus actual IndexedDB. Save source/learner reference values.
2. Open an additional raw IndexedDB **version 1** connection and deliberately hold it open when native `versionchange` is received, emulating an older document/tab that has not released its database connection. Request a native upgrade to version 2 **without changing or deleting any object store**.
3. Require actual `onblocked` and `versionchange` events, and prove the upgrade cannot complete until the held connection is closed. A missing blocked event is a test failure—not a simulated success.
4. Once the test-owned handle is closed, the upgrade proceeds. The isolated **version-1-only research adapter must refuse** an unknown newer version; it must not export an incomplete backup or suggest a Restore based on missing source data. Raw direct IndexedDB reads at version 2 must show original manifest, revision blob and historical alias records unchanged, with exact learner strings still present.
5. Close Chrome normally and launch a second independent Chrome process. It must still reject the unexpected schema version, while raw IndexedDB contains the original data and 73 synthetic attempts survive in localStorage.

**Strict boundary:** This uses genuine Chromium blocked-versionchange semantics, but the deliberately held connection is in the same test origin/document, **not a demonstrated two-tab app race**. The test deliberately upgrades the schema of **only a throwaway research database** and never deletes or rewrites source object stores. Actual Safari blocked/eviction behavior, version-migration compatibility, Safari multiple-tab races and real family recovery remain untested. It proves refusal and preservation, not successful migration to newer IDB schema.

## R4g extension — two independent native Chromium page targets

R4f held two IndexedDB connections **inside one document**. R4g closes this specific gap by running a controlled multi-page Chromium scenario in a **fifth throwaway browser profile**:

1. The first Chromium page restores a checksum-verified V2→V3 file containing the same three genuine public curriculum sources and **73 fake attempts**. It pins original learner strings and source counts in a real `localStorage` and IndexedDB database.
2. The first page opens a **second, independent same-origin Chromium page** using `window.open`. A test-only Chromium `--disable-popup-blocking` launch flag permits page creation without a user gesture; it does **not** bypass IndexedDB or Recovery validations. The Node driver independently enumerates CDP `/json/list` targets and must confirm **two distinct real page target IDs**, not merely two connections in one tab.
3. The first page deliberately holds its real IDB v1 connection open and handles `versionchange` without closing. The second page requests v2. Native `onblocked` fires **on the second page**, and native `versionchange` fires on the first. The driver checks both via CDP and only then invokes the owner page's test-only release callback. Any early completion, missing second page, or missing blocked event fails the gate.
4. Once the first tab releases the native old connection, the second page completes a **metadata-only** v2 schema transition. It checks exact original source blobs and aliases (not just counts), the 123 current lessons, identical original synthetic attempts/Writing/course state and the version-1-only adapter's refusal to read or export from the unknown schema.
5. After both page targets close normally, another Chrome process reopens the same disposable profile. It verifies original learner entry bytes, source inventory, and fail-closed response to incompatible IndexedDB schema.

**Strict scope:** This demonstrates genuine *two independent Chromium page contexts* contending for an IndexedDB version change. It does **not** prove concurrent learner writing/merge resolution, Safari/iPad multi-tab lifecycle, IDB eviction, crash/power-loss durability, or the production UI's own multi-tab coordination. No original family profile or Recovery file is used.

## R4h extension — genuine two-tab learner progress + Writing collision research

R4g exercises two Chromium tabs for IndexedDB **schema** contention, not concurrent user writes. R4h addresses the user-level lost-update risk in a **sixth disposable Chromium profile**, using exactly the same shape of English `academic-attempts` and learner `state` localStorage keys as a synthetic V2→V3 restore. **No production runtime writer is changed.**

1. Restore the public curriculum versions 1.18.0/1.18.1/1.20.0 and **73 entirely fictitious attempts** into real Chromium localStorage and IndexedDB. The original Writing review, original attempt evidence, score status, current source and historical rubrics are preserved.
2. Open a **second Chromium tab** of the same origin, verify two distinct DevTools `page` target IDs and matching original SHA-256 attempt/Writing snapshots. Both tabs hold stale in-memory values.
3. **Demonstrate the actual vulnerability, but only on a non-learner scratch key:** first tab writes its draft answer and Writing review, then second tab writes its own edits from the stale snapshot. Real `localStorage.setItem` performs last-writer-wins, causing loss of the first tab's changes. The real synthetic `academic-attempts` and Writing keys are **not touched** by this intentionally destructive step; the uniquely named scratch key is immediately removed.
4. **Test-only guarded proof:** both tabs use one native Chromium Web Locks exclusive name around the paired attempt+Writing keys. The first tab deliberately holds the lock; second tab queues a conflicting write. The CDP driver independently verifies its real second-page status, first-tab lock ownership and a **native Web Locks pending request** before releasing the first tab. The first tab writes its draft answer (attempt #72 of 73) and one review.
5. On acquiring the lock, the second tab's **stale snapshot compare** detects the changed source and **rejects without overwriting either key**. It then re-reads the winner, retries within the same exclusive lock and merges a distinct draft answer (attempt #73) and another Writing review. Explicit tests require original 71 unaffected attempts be **byte-equivalent**, both edits and both new reviews retained, original review retained in order, full normalized historical source untouched and verified V3 re-export including the updated synthetic records.
6. After a normal Chromium shutdown and fresh process, the merged learner bytes, history and complete V3 export must still verify. A missing real second tab, missing native Web Lock queue, silent stale overwrite or missing original data makes the gate **FAIL**.

**Research boundary:** This proves a cross-tab lost-update vulnerability of unguarded browser `localStorage` and a *prototype* serialization + stale-write veto/refresh strategy. The guarded writer exists **only inside this isolated test**. Existing LIVE app writers do not use this Web Locks prototype; therefore **production multi-tab safety remains UNPROVEN**. Native Web Locks availability across iPad Safari, multi-key atomicity under errors, actual simultaneous user submission semantics, UI reconciliation, restore interleaving, cross-device data and owner acceptance remain open. It is not a production bug fix or deployment authorization.

## R4i extension — interrupted two-key learner/Writing write with journal-based recovery

R4h showed that a native `navigator.locks` exclusive queue and stale-snapshot checks can protect against *concurrent tab* overwrites **only when the paired learner keys are written successfully**. It did not demonstrate interruption **between** writing the `academic-attempts` and learner `state` keys. R4i tests this separate failure boundary on a **seventh independent disposable Chromium profile**.

1. Start with authentic V2-format SHA-verified fixture derived from three public curriculum sources (1.18.0, 1.18.1, 1.20.0), **exactly 73 invented attempts**, and invented Writing feedback; normalize, checksum-verify and restore in a real Chromium origin. No real family iPad backup or profile is accessed.
2. While holding a real test-owned `navigator.locks` exclusive lock, write a **test-only preimage journal** containing the original exact attempt and Writing strings plus their SHA-256 hashes, a separate test-only pending marker in the non-production V3 adapter's English namespace, and then write **only the first** learner key. **Deliberately stop before writing Writing** or removing the journal/marker. This is a scripted interruption, **not** a real browser kill, OS crash, disk-full fault or Safari lifecycle event.
3. Confirm the original Writing key is still present, the attempt key alone changed and the pending marker exists. The R4i adapter extension explicitly excludes this marker from learner entries and rejects **both V3 export and V3 Restore preview** while that paired-write marker exists, even when the other source hashes are correct. This prevents a **falsely complete V3 backup** for the prototype.
4. Shut Chromium down **normally**; restart an independent process with the same disposable profile. It must find the exact same journal, SHA-256-pinned marker, old Writing bytes and half-written attempt bytes; a new V3 export must remain blocked. Inside the same test-only exclusive Web Lock, compare the current two keys against the journal's expected partial state, roll back **only** the changed attempt key, verify the **exact** original pair, then remove the pending marker and the temporary journal. Another complete V3 export must preserve all 73 original synthetic attempt values and original Writing/reviews unchanged.
5. Run a full **successful paired write**, again under a native Web Lock, with marker and journal written before the two learner keys. Once both keys match the planned values, clear the marker/journal. Require that the intended draft and Writing review both survive, the other 72 attempts stay unchanged, historic rubric/content revisions remain pinned, and a fully verified V3 export includes the new paired values.
6. After one more independent Chromium process restart, verify the paired attempt + Writing values, the unchanged academic source inventory, no pending marker/journal and a complete checksum-valid V3 backup.

**Critical limits:** The additional pending-marker check is in an **unmerged, detached research adapter**, not LIVE. The journal in this acceptance test uses extra `localStorage` space; a real product would require a reviewed quota-safe, tamper-resistant, versioned journal and durable recovery UI. Browser shutdown is **graceful** after the deliberately half-written state; R4i does **not** verify hard SIGKILL/power loss, true native quota failure on the *second* key, a transactional multi-key `localStorage` primitive (which does not exist), or Safari/iPad durability. While marker checking prevents known interrupted data from exporting, it cannot guarantee isolation if production writers ignore the marker or fail before it is persisted. This is **not a shipping fix** and does not authorize migrating learner storage.

## R4j — real native Chromium quota exhaustion on the **second** Writing key

R4i proved a scripted interruption between learner attempts and Writing; R4j extends that exact boundary with a genuine, measured browser `QuotaExceededError`, not a fault-injecting adapter or a mocked exception. All content is made from public curriculum sources 1.18.0/1.18.1/1.20.0, **73 invented** scored/draft attempts, and invented Writing reviews. A new, eighth **disposable Chrome profile** is isolated from all other tests, family data and LIVE.

1. Verify original-format V2 checksum, convert to verified V3, restore into real localStorage and IndexedDB, retain exact original 73 attempt strings plus Writing/course state, original revisions and rubric source.
2. Under a native Chromium exclusive Web Lock, persist a research-only **preimage journal** with SHA-256 references, set the non-production V3 `learner-write-pending-v3` marker and successfully write the **first** (`academic-attempts`) key.
3. Use **only a disposable scratch key outside the learner namespace** to binary-search the *actual Chromium localStorage capacity* after the first key. Reduce scratch padding slightly to preserve marker/journal. Write a larger valid JSON Writing update to the *real second* learner state key and require **native `QuotaExceededError` on that exact write**. If real quota cannot be reached, or the second write succeeds, FAIL. The previously existing Writing string must remain byte-identical; the first key and marker must remain in the half-written state.
4. Require V3 **backup export and Restore preview to fail closed**. Close Chromium normally; in a completely new Chromium process, require the exact original journal, marker, large scratch padding and incomplete two-key state survive. Export/preview must still be blocked.
5. Re-verify journal checksum and original exact learner strings under the same test-owned Web Lock. Roll back **only the modified first learner key** and verify both originals before removing the pending marker/journal. Remove **only the test-owned scratch padding after** exact original recovery. Then require complete verified V3 export with all 73 original attempts and original Writing review.
6. Demonstrate a fresh, successful paired write after storage headroom is released; require original other attempts and reviews preserved, historical lesson/rubric pinned, and full V3 Recovery export. Close Chrome normally, reopen it a third time and confirm both committed keys, full source and backup survive.

**Strict non-claims:** The native quota failure is genuine Chromium `localStorage`, but near-quota conditions are engineered with disposable scratch padding. This is neither Safari/iPad quota acceptance nor native IndexedDB quota/eviction. Chromium is shut down *normally* once the quota-induced interrupted state is reached: no real hard SIGKILL, crash or power-loss durability is claimed. The journal/marker lock writer is still an **isolated research fixture, not integrated into LIVE**, and the two-key localStorage operation is **not atomic**. Real quota may even prevent writing a full journal/marker before an update; that case remains a separate unresolved gate. No real family Recovery or attempts are touched.

## R4k — native quota BEFORE preimage journal or incomplete-write marker

R4j found recoverability when a full SHA-256-pinned journal and pending marker already exist **before** the second learner/Writing key fails. R4k addresses two earlier storage-failure boundaries **before a protected learner write can begin**, on a ninth independently disposable Chromium profile.

1. Restore verified authentic-format V2→V3 fixture from committed **public** 1.18.0/1.18.1/1.20.0 sources into actual Chromium IndexedDB and `localStorage`. Preserve **73 entirely fictitious** attempts, the original invented Writing review, course selection and historical revisions.
2. Under native Chromium Web Locks, fill **only a test-owned scratch key outside the learner namespace** to the *actual measured* `localStorage` capacity. Require a genuine browser `QuotaExceededError` on writing the full preimage journal. **Do not attempt marker or learner writes** if this journal cannot be durably recorded. Verify no marker/journal, no changed learner bytes, no damaged source; release only the test-owned scratch padding.
3. In the same isolated profile, store and read back the full preimage journal *successfully*; again measure real native scratch-key capacity. Now require a genuine `QuotaExceededError` specifically when attempting to write the smaller pending learner-write marker. **Abort before touching either learner key**, safely discard **only** the test-owned abandoned journal and then test padding. Confirm no false pending/partial recovery marker or changed learner bytes.
4. Verify that the full original V3 backup remains checksum-valid with exactly 73 original synthetic attempts, unchanged Writing/course state and original source/rubrics: unlike R4i–R4j, where learner keys truly diverged, **safe early preflight abort allows original complete backup**.
5. Close Chromium normally, restart a wholly independent browser process with the same disposable profile and independently verify original learner and IDB data, no scratch or pending journal/marker, and full verified V3 Recovery export.

**Boundary:** These are native Chromium localStorage quota errors created by **synthetic scratch padding**, not false injected exceptions. The test checks safety of a *test-only preflight sequence*. It does **not** establish that the existing production writer performs such preflight, that localStorage gives atomicity across multiple keys, or that a journal/marker is durable after abrupt OS kill or power loss. Safari/iPad, real household Recovery, original iPad attempts, actual IDB disk eviction and audio rights remain outside scope.

## R4l — actual Linux SIGKILL after first learner key: classify durable state

R4i/R4j/R4k use real Chromium, but close the browser **gracefully**. R4l creates a **tenth isolated throwaway Chromium profile** to test real OS-level `SIGKILL`, **without** the Chromium `Browser.close` shutdown protocol. The external Node QA driver launches the crash-only Chromium browser as a **detached Linux process group**, waits for the browser's exact staged learner/journal bytes and a blocked V3 export, kills **the entire browser process group** with `process.kill(-pid,'SIGKILL')`, and verifies the main process reported `SIGKILL`. No other browser QA profiles or user data are touched.

1. First, create an **already durable baseline** with a checksum-verified original-format synthetic V2→V3 source from the public 1.18.0/1.18.1/1.20.0 curriculum: 123 active lessons, historical aliases/rubric blobs, **73 invented attempts** (52 scored/21 drafts), original fake Writing review and course selection. **Shut this baseline browser down normally** so the historical starting point is persistent.
2. In a second Chromium process using that exact throwaway profile, enter a real native `navigator.locks` exclusive lock and write a full SHA-256 preimage journal, a separate incomplete-write marker, then update **only** the first `academic-attempts` key; do **not** update the second Writing key. Read back the marker, journal and half-write; require V3 backup rejection before giving the driver the kill-ready signal.
3. The external driver kills Chrome's process group with genuine Linux `SIGKILL` **after the page's readback**, bypassing normal browser shutdown, and confirms the kill signal.
4. A fresh third Chromium process reads **actual durable bytes**, without assuming `localStorage.setItem` is equivalent to disk fsync. The QA classifies:
   - **ORIGINAL_ALL_ABSENT:** none of the pending journal/marker/first-key update survived; both original learner values are intact. Safe discard of an uncommitted edit.
   - **ORIGINAL_WITH_VERIFIED_JOURNAL:** original learner bytes survived, with a complete verifiable journal and optional valid marker; protected cleanup is allowed.
   - **PENDING_PAIR_VERIFIED:** only the first learner update survived, **and the complete matching SHA-256 journal and marker also survived**. Incomplete V3 backup and Restore preview must stay blocked; rollback under native Web Lock restores exactly the original two keys before clearing the marker/journal.
   - **UNSAFE / FAIL:** a modified learner key survives with journal or marker missing/incorrect; unknown partial learner bytes, orphan/mismatched marker, lost historical source, missing course selection, or a restored backup lacking original fake attempts. The gate must **FAIL CLOSED**, not rewrite or bless this state.
5. Following recovery or a clean original state, a full SHA-256-verified normalized V3 backup must again preserve all **73 exact original** fake attempts, old Writing feedback and historical source. A **fourth independent Chromium process** confirms the recovered state and portable backup remain intact after a subsequent normal browser restart.

**Boundary:** This is a **real Linux process-level SIGKILL** but still not a machine power cut, filesystem crash or iPad WebKit kill. It measures **one particular timing** (first-key browser readback) rather than the entire crash window. A PASS would mean the specific observed durable state was safe under the gate; it **cannot** prove localStorage journal+marker ordering/durability in general or shipping transaction atomicity. An UNSAFE/FAIL result should be recorded openly as a blocker. Journal/marker remain in a **detached, non-production research adapter**, not active learner-writer code. The test never inspects family records.

## Explicit non-claims / blockers

- SHA verifies integrity of archived JSON, but it is **not a cryptographic signature proving the real provenance of the original learner data**.
- Real **MP3 binary digests and source-specific audio provenance** are not verified by this test. Transcript persistence is not evidence of actual audio playback.
- No true iPad/Safari quota, IDB eviction, Safari lifecycle, production concurrent learner write safety or power-loss/crash behavior is proved here. **R4h measures real two-tab localStorage lost updates; R4i tests interrupted two-key writes with a prototype marker/journal across graceful Chrome restarts. Neither is deployed in the app.**
- No private family Recovery V2 or original 73 iPad attempt records were opened. The generated 73 rows and feedback are fake.
- No production UI entrypoint to V3, no owner acceptance, no approval for source deletion or auto-migration.

**Release status stays NO_GO.** Maintain the existing V2 route, original media, learner data and v1.25 LIVE. Reconcile the stacked research code and complete media, Safari, interruption and owner-device gates before considering LIVE changes.
